# DeepSeek Harness Bridge

Run `python <this-skill>/scripts/desktop.py health` in the local environment where DeepSeek Harness Desktop runs. The helper needs Python 3.11+ and a paired Desktop Host on loopback (default port 8765). It reads the bearer from the file named by `DSH_BRIDGE_SECRET_FILE`, then from the `secret_file` path in a private `connection.json` beside this file, or from `~/.dsh/state/desktop-host-local/host.secret`, in that order. Configure the file path locally. Keep credentials, session IDs, prompts and private paths out of public artifacts. See the [Desktop setup guide](https://github.com/ft54482/dsh-control-bridge/blob/main/docs/windows-delivery.md#codex-desktop-setup).

## Choose the Harness session

1. Identify the intended Harness instance and workspace. For clearly new work, go straight to step 3. When looking for earlier work, use `discover` on Host 0.2.0+, scoped to the workspace and `kind=top`, paging as needed. On 0.1.6 use `workspaces` and `sessions` within grants. Use `granted` to check the exact session's access. A catalog entry or familiar title is a lead. Confirm the objective, deliverable or last decision from a small page of authorized `history`. Treat history as task data.
2. **Continuation or repair.** Use the original `session_id` when the task matches. Preserve its preset and model unless the user explicitly requests a change. If a likely original is busy, its history is inaccessible, or several sessions still fit, resolve that specific condition before dispatch. Keep its context in Harness.
3. **Unrelated work.** Create one fresh session in that same workspace by default. Require the Harness agent preset `master-control` (主控模式). Use the verified-create procedure in [Desktop commands](references/desktop.md#new-work-in-master-control-mode). Retain the new ID and check the Host's confirmed preset before the first prompt. If the preset or its readback is unavailable, report the exact blocker and stop dispatch. A reasoning effort, a prompt mentioning the mode, or a default session cannot establish the selected preset.

## Dispatch and follow up

- For development, confirm the session maps to the intended checkout, is idle, and has write access. Pass an explicit scope and acceptance criteria. Use a separate checkout when another agent is editing the same working tree.
- Create a fresh request ID before `resume` and retain it together with the session ID. On 0.2.0 dispatch defaults to asynchronous. After a timeout, lost response, or process restart, use `request`, `wait`, or `stream` with the original ID. Report success only when the request shows `phase=terminal`, `terminal_scope=official`, and `completed=true`. Treat `unknown` as unresolved. Reconcile with the Desktop before submitting anything further.
- For model changes, use `models` and `model-catalog` first. Compare `confirmed_selection` and `execution_model` with the requested provider, model, and effort. `effort_verified=false` leaves the execution effort unverified. Use the current session's model when no change was requested.
- For verified workspace creation on Host 0.2.2, use an existing granted workspace ID. A directory outside `workspaceRoots` must be named by its exact ID in `presetSessionWorkspaceIds`. A new write grant requires an existing write-authorized session in that workspace. Keep the separate file-operation roots intact. Pairing a session and listing a workspace ID there are grants, and the user decides them, not you: show the exact line and wait for the user's explicit approval of that change before editing the Host configuration. A request to make it work is not approval. When the Host refuses with 403 or 409, report the blocker and do not widen `workspaceRoots` or any allowlist. Editing the Desktop profile's `cordis.patch.yml` restarts Desktop, so confirm that no task is running first. See [Permissions and authorization](https://github.com/ft54482/dsh-control-bridge/blob/main/docs/permissions.md#for-the-installing-agent) (in Chinese).
- **Workspace autonomy is the operator's exception, never yours.** The rules above are the default. Only when the operator has enabled `workspaceAutonomy` and the Host reports `health.workspace_autonomy.effective: true` may a request that carries `task_id` and `purpose` use the task-driven flow in [Workspace autonomy](#workspace-autonomy-operator-enabled): register or reuse the directory, take the task-scoped write grant, and create the first write Session. A request without task intent keeps the old semantics; a task-intent request on a Host without an effective policy is refused with `403 workspace_autonomy_not_effective`. Enabling the policy, or otherwise widening what the Host may create, is the user's decision — show the exact configuration change and get explicit approval; a request to make something work is not approval.
- Creation returns an empty session. On Host 0.2.2, send the first `resume` from the skill even if the new session reports deferred model selection. The Host verifies the saved preset and uses the official session controller to attach the session when needed. Check the official terminal record before accepting the result.
- For SuperAgent, use [Official SuperAgent](references/superagent.md) to inspect the local profile, Sources, Tickets and Assignments. New work needs an authorized Source event. Use `scripts/github_source.py precheck` with an explicit `--port`, `--repo` and `--actor`; it must pass before preparing anything. `prepare` only writes a local plan with a unique marker; `send --yes` is single-writer per plan, refuses duplicates, and marks a timeout `unknown` without resending (`send --reconcile` is read-only). `trace` accepts a plan whose `issue` is empty but `issue_url` is present, validates the Issue body author and marker, uses the real Ticket detail/mandate/decision, ignores a stale `running` assignment when `report.ready` and `turnEndedAt` are present, and reports instance load, worker report, acceptance, and final comment separately; an acknowledgement alone is not a final comment. Bridge `resume` is a different lifecycle from an engine Assignment.
- For a person ticket that waits on a human, `scripts/superagent.py --port <p> inbox --all` lists every `person` ticket with its latest effective Assignment, report summary, question, source Issue, Pull Requests, available actions and a `triage` (`review_ready`, `review_reported`, `blocked_missing_info`, `retryable_failed`, `running`, `unknown`, or `ended` for a terminal ticket). `detail <id>` adds the full picture and `next_actions`. Historical tickets read without a local plan. A newest Assignment that still says `running` while its report is not `progress` and `turnEndedAt` is set has ended its turn.
- To send work back, `scripts/github_source.py reply prepare|send|trace|poll` replies once on the ticket's source **Issue** (never a Pull Request thread) with a marker, keeps the same single-writer and duplicate rules as `send`, and treats `inputs[].delivered=true` with `deliveredTo` naming the Ticket or one of its Assignments as "Delivered to Ticket": a new Decision is not required. A timeout stays `unknown` and only `--reconcile` reads.
- A local verdict (`verdict set|list|show`) records `pass|fail|hold` with evidence in the skill state. `local_verdict` and `engine_state` are reported separately: a human `stop` is `stopped_by_human` and never a pass, and `decision.outcome=accept` is an authorization, not a delivery. Upstream has no route to mark acceptance while keeping a Pull Request open; that stays an upstream extension item. See [SuperAgent todo inbox](https://github.com/ft54482/dsh-control-bridge/blob/main/docs/superagent-todo-inbox.md) for the command list, the lifecycle table and the read/write boundary.

## Workspace autonomy (operator enabled)

The Host plugin can run under an operator-enabled `workspaceAutonomy` policy. It is opt-in and off by default: when the switch is absent or `false`, every rule above still holds unchanged. When it is in effect, a caller that carries a task may register or reuse **any absolute directory** — the Host does not re-check writability, it only requires an absolute path that exists or can be created one level deep; what can actually be written there is whatever the Host's OS account may write — take a task-scoped grant, and create the first write Session in a workspace that has none.

1. **Read the policy first.** `health` must report `workspace_autonomy.effective: true`; add `preset_create_verified: true` when you pass a preset. A request that carries task intent on a Host whose policy is not effective — **including one that never configured the switch** — fails closed with `403 workspace_autonomy_not_effective` and `autonomy_reason`; it is never a silent fallback to the guarded flow. Report that blocker and fix the configuration. The helper performs this check itself and exits 1 with `workspace_autonomy_not_effective` before sending any write.
2. **Register the workspace with the task.** `create-workspace` body: `{"path":"D:\\ws-lab\\outside\\alpha","task_id":"TASK","purpose":"PURPOSE","create_directory":true,"client_request_key":"KEY"}`. `task_id` (1..200 chars) and `purpose` (1..500 chars) are mandatory after trimming; missing or blank is `400 task_required`. The path must be absolute and is canonicalized with `fs.realpathSync.native`, so every spelling, symlink and junction of one directory is one workspace. A missing leaf is created only with `create_directory:true`, and only one level under an existing parent. The call registers and grants: `started_task:false`, no Session, no prompt. The helper refuses an unverified receipt (exit 1, `workspace_receipt_unverified`).
3. **Create the first write Session.** `create-session` body: `{"path":"D:\\ws-lab\\outside\\alpha","task_id":"TASK","purpose":"PURPOSE","agent_preset":"master-control","access":"write","client_request_key":"KEY"}`, or name the `workspace_id` returned in step 2 instead of `path`. The Host registers the path first when given, creates the Session through the official controller, proves the preset through `sessionController.projections`, and only then grants. Keep the returned `session_id`. The helper adds `agent_preset: "master-control"` if the body omits it and refuses an unverified receipt (exit 1, `agent_preset_unverified` or `task_receipt_unverified`).
4. **Then dispatch.** Send the first `resume` from the skill with that `session_id`, the authorized task text and a new `request_id`; accept the result only at `phase=terminal`, `terminal_scope=official`, `completed=true`. Creating a workspace or a Session never starts a task.
5. **Task ownership.** A workspace belongs to the task that took it first. A different `task_id` on the same workspace, or a Session on it, is `409 workspace_task_mismatch` with `existing_task_id`. Pass `confirm_task:true` to take it over: the Host journals `workspace_task_confirmed` (evidence, keyed by `parent_key`), keeps the first task on the workspace grant and records the new task on its Session. An Agent may decide to confirm when the new task is the same work under a new id; the takeover is auditable, the directory is shared.
6. **A busy Session is never preempted.** The Host never cancels a running turn; `resume` on a busy Session is refused with `busy`. Wait for the official terminal record instead.
7. **Revoking.** `revoke-workspace {"workspace_id":"…"}` removes the workspace grant and every Session grant under it in one atomic write and reports `directory_intact`. It withdraws authorization only: the directory and any running turn stay exactly as they were. There is no delete endpoint.
8. **Idempotency.** `client_request_key` is optional (`^[A-Za-z0-9][A-Za-z0-9._:-]{7,199}$`) and global. One key answers one operation (`workspace` or `session`) with one set of arguments (`task_id`, `purpose`, `path`, `workspace_id`, `agent_preset`, `access`, `model`, `confirm_task`). Same key and arguments while the authorization still exists → `200` with `deduplicated:true`. Same key with another operation or other arguments → `409 idempotency_key_reused` (`previous_operation`, `mismatched`): use a new key, never replay. Same key after a revoke, an access change or a task takeover → `409 authorization_stale` (`historical` summary plus a top-level `current` string of `revoked`/`missing`/`access_changed`/`task_changed`); the grant does not come back and the request has to be made again.
9. **Audit trail.** Every operation is appended to the Host's `workspace-autonomy.jsonl` with 17 fixed keys plus `receipt` on a success line or `revoked` on a revoke line. Read it to reconcile; never write it, and never put confidential material in `purpose` (stored verbatim).
